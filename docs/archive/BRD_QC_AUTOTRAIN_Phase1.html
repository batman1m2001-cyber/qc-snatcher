1. Mục tiêu & phạm vi Phase 1

Executive Summary

Nội dungChi tiết
Mục tiêuQC ghi nhận trường hợp AI đánh giá sai → dữ liệu tự động đưa vào training pool AI → AI tự cải thiện qua thời gian.
Đầu vàoFeedback issue do QC tạo trên VQC UI (theo Turn hoặc theo Tiêu chí).
Đầu raCorpus AI được cập nhật; các cuộc gọi đã note được rescore bằng phiên bản mới; QC-BU thấy được hiệu quả xử lý.
Scope Phase 1Auto append feedback vào training pool
Scope Phase 2Cho BU tự custom prompt + corpus (không nằm trong tài liệu này)

In scope — Phase 1

  • QC note issue ở 2 điểm: Transcript (theo Turn) và Kết quả AI (theo Tiêu chí).
  • IT truyền feedback issue sang EDA cùng với danh sách call.
  • EDA đọc feedback → tự động append vào training pool.
  • Rerun cuộc gọi đã note sau khi EDA update → đối soát trước/sau fix.
  • Realtime dashboard theo dõi trạng thái xử lý issue.

Out of scope — Phase 1

  • BU custom prompt / corpus qua UI (Phase 2).
  • Review gate / approval workflow (Phase 2).
  • Rollback UI cho corpus (Phase 2).
  • Xử lý lỗi data quality (Sai ASR, tạp âm, sai người nói) — không đi vào training pool, cần route sang team ASR / pre-processing riêng.

4.2. QC label — 3 giá trị

Quyết định feedback đi đường nào ở phía EDA:

QC label (UI hiển thị)Ý nghĩaBackend action
Vi phạm — AI bỏ sót Turn/tiêu chí này thực sự vi phạm nhưng AI không bắt. Thêm vào training pool dạng positive sample.
Tích cực — AI gán nhầm Turn/tiêu chí này bình thường nhưng AI báo vi phạm. Thêm vào training pool dạng carveout sample.
Không liên quan (Sai ASR / tạp âm / sai người nói) Lỗi hạ tầng, không phải lỗi của model. Log vào queue riêng, không vào training pool. Route sang team ASR/pre-processing.

5. Kiến trúc lưu trữ Corpus — 2 option + đề xuất

Đây là điểm cần chốt rõ giữa IT + EDA. Có 3 option:

Tiêu chí Option A — Corpus lưu DB dùng chung Option B — EDA quét data zone định kỳ Option C — Hybrid (đề xuất)
Feedback issue lưu ở DB dùng chung (IT + EDA cùng schema) File JSON trong data zone (IT push cùng call list) DB IT (transactional)
Training pool (corpus) lưu ở Cùng DB dùng chung Git repo EDA (file corpus.yaml) Git repo EDA (file corpus.yaml)
Cách EDA lấy feedback SQL trực tiếp Scan folder / bucket định kỳ Gọi API IT (REST)
Version control training pool Cần migration + version table Git — sẵn có audit trail Git — sẵn có audit trail
Realtime dashboard cho QC Dễ — query trực tiếp DB Khó — file-based, phải sync ngược Dễ — query DB IT
Complexity infra Cao — DB shared cần permission phức tạp, IT + EDA cùng write Trung bình — cần polling + retry Thấp — interface REST rõ ràng
Rủi ro corpus bị corrupt Cao — nhiều bên write cùng lúc Thấp — EDA duy nhất write Thấp — EDA duy nhất write
Rollout time Lâu (schema alignment) Nhanh Nhanh
Đề xuất: Option C (Hybrid)
  • IT giữ quyền sở hữu bảng feedback_issue trong DB nội bộ — hỗ trợ tốt realtime UI + dashboard cho QC.
  • EDA giữ quyền sở hữu training pool (corpus.yaml trong git) — audit trail bằng git history, rollback dễ.
  • Interface giữa 2 bên là REST API (xem §6) — decoupled, không phụ thuộc schema DB của nhau.
  • Không cần DB dùng chung → tránh vấn đề permission + concurrent write.
Lưu ý về Option B: Nếu chọn Option B (data zone push kèm call list), IT vẫn cần thêm cơ chế notification khi có issue mới để EDA không lag quá. File-based delivery kém realtime, khó cho tính năng realtime dashboard trong BRD gốc.

6. API contract IT ↔ EDA

Nếu chọn Option C — đề xuất 3 endpoint tối thiểu:

6.1. GET /qc/feedback-issues — EDA pull issue

ParamÝ nghĩa
sinceISO timestamp — chỉ lấy issue tạo/update sau thời điểm này
statusFilter (mặc định new,pulled)
limitSố record tối đa

Response — array các feedback_issue (schema §4.1) + metadata call kèm theo (tối thiểu: calltrace_id, call_code, agent_username, call_date, queueid, is_chinh_chu, closed_by — cùng bộ field trong metadata.py hiện tại).

6.2. PATCH /qc/feedback-issues/{id} — EDA update status

Body:

{
  "status": "in_training | rejected | done",
  "reject_reason": "...",           // optional
  "corpus_ref": "step42_20260727",  // optional — section trong corpus.yaml
  "rerun_verdict": {                 // chỉ set khi status=done
    "before": { "violation": true,  "category": "C1", "reason": "..." },
    "after":  { "violation": false, "category": null, "reason": "..." }
  }
}

6.3. POST /qc/rescore-request — EDA báo IT chạy lại

Body:

{
  "calltrace_ids": ["...", "..."],
  "training_pool_version": "v4-corpus-20260727",
  "requested_by": "eda-team"
}

IT trigger rescore trên các call này (dùng phiên bản model mới nhất), sau đó cập nhật kết quả bằng endpoint §6.2.

7. Đối soát sau Fix

7.1. Yêu cầu

  • Với mỗi issue đã đi vào training pool, hệ thống phải rerun cuộc gọi đó bằng phiên bản AI mới.
  • UI hiển thị 3 kết quả song song:
    1. Kết quả AI trước fix — verdict cũ (đã lưu khi call được scan lần đầu).
    2. Kết quả AI sau fix — verdict mới sau rerun.
    3. Kỳ vọng của QC — chính là qc_label QC đã note.
  • Trạng thái Issue → done chỉ khi sau-fix trùng với kỳ vọng QC.

9. Open questions — cần chốt với các bên

  1. Chọn Option A, B hay C? — đề xuất C, cần IT xác nhận có build được API layer không.
  2. Tần suất pull của EDA — realtime (webhook) hay batch (nightly / hourly)?
  3. QC có được sửa lại issue đã note không? — nếu có, cần versioning trên feedback_issue.
  4. Ai chịu trách nhiệm route lỗi data-quality (Sai ASR, tạp âm)? — cần team owner rõ ràng, không thì lỗi loại này sẽ tồn đọng.
  5. SLA rescore — sau bao lâu kể từ khi QC note thì phải có kết quả đối soát? (Đề xuất: 24h.)
  6. Rollback policy — nếu 1 batch training pool làm AI tệ hơn, cơ chế revert như thế nào? (Có thể defer sang Phase 2.)
